# Pencil contribution-fork audit - 2026-09-30

## Scope and verdict

Audited `Markus-web/pencil-by-rino-contrib` at upstream/fork `main`
`1cd6933190032dcf2be91c423406e89ca79d1b7b` and the seven open `pr/*`
branches, both individually and as one clean combined tree.

The seven contributions are narrowly scoped, mutually mergeable, free of
private branding/secrets, and PHP-syntax clean. No confirmed stored XSS or
protocol-filter bypass was found. The repository still inherits four
authorization, concurrency, and storage-assurance gaps from upstream. They are
not regressions introduced by the seven PRs.

## Findings

| ID | Priority | Finding | Required remediation |
|---|---|---|---|
| PENCIL-AUD-01 | Medium | The REST save gate checks `edit_pages`, but a `page-{id}.*` field does not require `edit_post` for that page. A restricted role admitted through `pencil_can_edit` can cross the intended page ownership boundary. | Store/recover the scoped post ID and require `current_user_can('edit_post', $post_id)` before saving. |
| PENCIL-AUD-02 | Medium | `pencil_values` is one whole-option read/modify/write. Concurrent saves to different fields can both return success while the later write loses the earlier change. | Serialize saves with a per-site lock and refresh the option cache after acquiring it. |
| PENCIL-AUD-03 | Medium | PR #2 caps the final option at 1 MiB and PR #4 keeps 500 records, but activity rows retain full old/new values. History can approach roughly 1 GiB per site, and raw markup is processed before a raw-body bound. | Reject oversized raw field values before sanitization and truncate each stored history snapshot with full-length/digest metadata. |
| PENCIL-AUD-04 | Low/Medium | REST/editor access honors `pencil_can_edit`; the admin History page checks only `edit_pages`. A host filter that denies Pencil can still leave direct access to full before/after history. | Make the page callback fail closed through `Pencil_Plugin::can_edit()` as well. |

Security fixes should be coordinated privately with upstream before publishing
exploit details. Equivalent fixes and red/green behavior proofs exist in the
private production fork; that fork is evidence, not an upstream release.

## Evidence

- All seven branches and their combined cherry-pick pass `php -l` and
  `git diff --check`; CSS braces and parentheses balance.
- Semgrep scanned 21 files with zero findings or errors.
- Gitleaks scanned 18 commits with zero leaks.
- Trivy found no dependency/configuration target because the plugin has no
  package manifest or vendored dependency tree.
- An unauthenticated WordPress Playground request to the mutation route was
  rejected with `401 rest_forbidden`.
- GitHub secret scanning and push protection were enabled; no secret alert was
  observed through the available repository API.
- The Strix combined-tree review was deliberately stopped by its safety cap at
  8,082,289 input tokens. Status is `interrupted`; it filed no validated
  vulnerability before stopping. This is incomplete coverage, not a clean
  exploit assessment.

## Repository assurance gaps at audit time

- No CI/status checks or retained regression suite.
- No branch protection on fork `main`.
- GitHub code scanning and dependency alerts disabled.
- GitHub license detection returned `NOASSERTION` for the inherited license
  file even though plugin metadata and README declare GPL-2.0-or-later.

The reusable `scripts/verify.sh` gate and quality workflow were added after the
audit to close the first gap, and GitHub vulnerability alerts were enabled.
Code scanning has no PHP analyzer configured. Branch protection and upstream
disclosure remain repository-owner/process decisions.
